# Writing keecas calculation notebooks

This skill captures the conventions for `__*.ipynb` notebooks in a keecas-based Quarto report. The notebooks are not generic Jupyter — they are a domain-specific authoring format where **every numeric result must be traceable to a symbolic expression that the reader sees on the page**. Most violations come from treating keecas like an optional display layer instead of the substrate.

## The core principle (read this before writing any code)

The rendered PDF shows formulas and numbers side by side. If a number on the page comes from a numpy sidecar computation rather than the symbolic expression next to it, the two can drift — the formula could be edited and the number would silently not update (or vice versa). The conventions below all exist to make sure **the formula you display IS the formula that produced the number**.

Concretely this means:

- Expressions live in an `eqn` dict as sympy objects (usually built via `pc.parse_expr` from strings).
- Numeric values are derived from those expressions by piping through `pc.subs(eqn | params) | pc.convert_to([...]) | pc.N`.
- `show_eqn` is the single rendering entry point: it shows symbol → formula → value → description in one table.
- Plain `print()`, raw numpy computation of values, and side-channel `params[x] = ...` of computed quantities are all anti-patterns.

If your code starts doing arithmetic with floats and assigning back into `params`, stop — you've left the rails. Define the relationship in `eqn`, compute `_v` via the pipeline, and let `show_eqn` display it.

## The conventions

### 1. Init cells — same order, every notebook

The first three code cells are always:

1. **Imports + `PATH_PREFIX`**, tagged as `inizializzazione`:
   ```python
   #| tags: [inizializzazione]
   #| label: INIZIO CALCOLO <SCREAMING_SNAKE_CASE_NAME>

   import matplotlib.pyplot as plt
   from keecas import *
   from keecas.label import generate_unique_label

   from ruamel.yaml import YAML
   yaml = YAML()
   yaml.preserve_quotes = True

   from pathlib import Path
   from IPython.display import display, Markdown

   try:
       PATH_PREFIX
   except NameError:
       PATH_PREFIX = './'

   PATH_PREFIX = Path(PATH_PREFIX)
   ```

   `generate_unique_label`, `display`, `Markdown` are imported here at the top — not deep inside a later cell.

2. **keecas config + result dict**:
   ```python
   config.latex.eq_prefix = "eq-<SECTION>-"
   config.display.print_label = True
   config.display.katex = True

   <SECTION> = {
       "parametri":   (params := {}),
       "espressioni": (eqn    := {}),
       "valori":      (vals   := {}),   # add if downstream notebooks consume computed values
       "verifiche":   (verifiche := {}), # add only for verifica notebooks
   }
   ```

3. **KaTeX include** (one-liner Quarto include, not a code cell):
   ```
   {{< include /_scripts/_KaTeX_compatibility.qmd >}}
   ```

If the notebook depends on a shared base (e.g. materials, snow base), the `%run` cell goes **before the init cells — as the very first cell in the notebook**, never after:

```python
#| output: false
#| eval: false
%run ../../shared/__materiali.ipynb
```

Putting it first avoids two independent clobbering failures:

- **Local symbols/params** — if `%run` fires after locals are already defined, the base notebook's `symbols(...)` calls overwrite them.
- **Global `config.*` settings** — the base notebook's own init cell sets `config.latex.eq_prefix`, `config.display.katex`, etc. If `%run` fires *after* the current notebook's own config cell, those settings get silently overwritten by the base notebook's values (e.g. `eq-SOVRACCARICHI-` reverting to `eq-NEVE-`), and every `show_eqn` call from that point on renders under the wrong label prefix. The base notebook does its own `from keecas import *`, so nothing in it depends on the current notebook's init cell having run first — there's no cost to running it before everything else, and the current notebook's own init/config cells (which always run after) get the last word.

Both cell options matter:

- `#| output: false` — the cell produces no visible output in the rendered PDF.
- `#| eval: false` — the cell is *not executed* at render time. Quarto renders the project as a single Jupyter session, and the parent notebook (`__materiali.ipynb` in the example) has already been executed and its namespace is already in memory by the time this cell would otherwise fire. Re-running it would do double work at best, and at worst re-clobber values that downstream cells have already overridden. The `%run` cell is purely a *development* convenience for executing the notebook in isolation.

### 2. Symbol declaration — r-strings always

```python
# Good
q_s, mu_i = symbols(r'q_{s} \mu_{i}')
alpha     = symbols(r'\alpha')
A_s_min   = symbols(r'A_{s\,min}')          # \, for in-symbol whitespace
dc_dev    = symbols(r'{\Delta\ c_{dev}}')   # braces wrap multi-token symbol
mu_1      = symbols(r'\mu_{1}', cls=sympy.Function)

# Bad — bare strings, missing braces, raw commas
q_s   = symbols('q_s')          # renders as q_s instead of q_{s}
alpha = symbols('alpha')         # renders as the word "alpha"
delta, c_dev = symbols(r'\Delta c_{dev}')  # space splits — yields TWO symbols
```

Rules: r-string, `{}` around multi-char subscripts, `\` for Greek, space-separated for multiple symbols, `\,` or wrapping braces for whitespace inside one symbol name.

### 3. The expression → values flow

The canonical block is three dicts and one `show_eqn`:

```python
# Symbols
A_s_min, k_c, sigma_s = symbols(r"A_{s\,min} k_c \sigma_s")

# Expressions (symbolic)
_e = {
    A_s_min: "k_c * f_ct_eff * A_ct / sigma_s" | pc.parse_expr,
}
eqn.update(_e)

# Descriptions
_l = {
    A_s_min: "minimo per controllo fessurazione",
}

# Values (derived via the pipeline — NEVER computed in parallel)
_v = {k: v | pc.subs(eqn | params) | pc.convert_to([u.mm]) | pc.N for k, v in _e.items()}

# Render
show_eqn(
    [_e, _v, _l],
    label=generate_unique_label(_l),
    float_format=[None, None, "{:.2f}"],
)
```

**Why this exact pattern?**

- `_e` is the symbolic source of truth; `eqn.update(_e)` keeps it available for downstream notebooks.
- `_v` is computed by a comprehension over `_e` — the formula and the number cannot drift apart.
- `_l` provides descriptions and (via `generate_unique_label`) LaTeX cross-reference anchors. Pass it to `label=` even when you don't render it as a column.
- The slot order `[_e, _v, _l]` matches the visual order on the page: formula, value, description.

**Where descriptions live — column vs. markdown.** `_l` values are wrapped in LaTeX `\text{...}` when rendered as a column, so they should be **short, LaTeX-clean strings** — not prose with parenthetical asides, and not inline math (`$...$` inside `\text{}` does not always render). As a rule of thumb:

- **For `_p` blocks (parameters)** — the symbol/value pair is narrow, so the `_l` column has room. Include it in the slot list: `show_eqn([_p, _l], ...)`.
- **For `_e` blocks (expressions evaluated to `_v`)** — the formula column can be wide and a description column risks overflowing the page width. Drop `_l` from the slot list and put a brief description in the *markdown cell immediately above* the code cell. Still pass `_l` to `label=generate_unique_label(_l)` so the cross-reference anchors are built.

```python
# Parameters block — _l as column is fine
show_eqn([_p, _l], label=generate_unique_label(_l))

# Expression block — formula is wide, describe in markdown above, _l only for labels
show_eqn(
    [_e, _v],
    label=generate_unique_label(_l),
    float_format="{:.2f}",
)
```

When you do keep `_l` in the slot list for an expression block (e.g. because the formulas are narrow), keep each entry to a short phrase: `"minimo flessionale - faccia inferiore"`, not `"prima soluzione dell'equazione di tangenza esterna, in gradi"`.

**Variant when you also have raw parameter inputs** (`_p`): merge them into the first slot so all keys produce rows:

```python
_p = {f_ck: 25 * u.MPa, f_yk: 450 * u.MPa}
params.update(_p)

_e = {f_ctm: "N(0.30) * (f_ck/u.MPa)^(2/3) * u.MPa" | pc.parse_expr}
eqn.update(_e)

_v = {k: v | pc.subs(eqn | params) | pc.convert_to([u.MPa]) | pc.N for k, v in _e.items()}

show_eqn([_p | _e, _v, _l], label=generate_unique_label(_l), float_format=[None, None, "{:.2f}"])
```

The `_p | _e` merge is essential: `show_eqn` uses the first slot to decide which keys become rows, and silently drops keys that appear only in later slots. See `references/show_eqn.md` for the full mechanics.

### 4. No parallel numpy computation of values

This is the single biggest trap. **Do not** strip units to floats, run numpy, then re-attach units and assign into `params`:

```python
# BAD — bypasses the symbolic chain
_x1 = float(params[x_1].to(u.m).magnitude)
_y1 = float(params[y_1].to(u.m).magnitude)
_d  = np.hypot(_x2 - _x1, _y2 - _y1)
params[d] = _d * u.m                       # number disconnected from any displayed formula

# GOOD — formula and value flow from the same source
_e = {d: "sqrt((x_2 - x_1)^2 + (y_2 - y_1)^2)" | pc.parse_expr}
eqn.update(_e)
_v = {k: v | pc.subs(params) | pc.convert_to([u.m]) | pc.N for k, v in _e.items()}
show_eqn([_e, _v])
```

The numpy path is fine for *visualisation* (plotting trajectories, evaluating a function at hundreds of points) but never as the source of a number that ends up in the report.

When you genuinely need a Python-side numeric value (e.g. to feed a `solve()` or to branch logically), extract it *after* the symbolic computation:

```python
_d_val = float((d | pc.subs(eqn | params) | pc.convert_to([u.m]) | pc.N).args[0])
```

### 5. Units — basic units only in `pc.convert_to`

```python
# GOOD — sympy raises the unit to the correct power from the quantity's dimensions
pc.convert_to([u.mm])         # areas → mm², lengths → mm
pc.convert_to([u.cm])         # areas → cm², inertia → cm⁴
pc.convert_to([u.kN, u.m])    # moments → kN·m

# BAD — compound units don't work
pc.convert_to([u.mm**2])
pc.convert_to([u.kN * u.m])
```

### 5a. Trigonometry and angles — `pc.convert_to([1])`, not `[u.rad]`

SymPy's trig functions (`sin`, `cos`, `asin`, `atan2`, ...) are quirky about angles: they assume their argument is in radians, but they require it to be a **dimensionless number**, not a quantity with `u.rad` attached. Likewise the result is dimensionless, not unit-bearing.

Two corollaries follow:

1. **Never multiply a trig result by `u.rad`** to "give it a unit" — the dimensionless form *is* the convention. `asin(k_e) * u.rad` looks tidy in source but tangles up the next computation that consumes the result.
2. **Strip units before trig consumes them.** When a quantity carrying `u.deg` (or any unit that should cancel out) is passed into a trig pipeline, convert to dimensionless first:

   ```python
   # GOOD — converts 30° to its dimensionless radian-equivalent number
   30 * u.deg | pc.convert_to([1])         # → π/6 ≈ 0.5236 (dimensionless)

   # BAD — keeps the deg unit; sin() of a unit-bearing arg won't simplify
   30 * u.deg | pc.convert_to([u.rad])
   ```

   When a trig argument is a ratio of like-unit quantities (e.g. `(y_2 - y_1) / d`), the ratio is *mathematically* dimensionless but SymPy may not auto-simplify the units. Be explicit by writing the trig argument as a ratio of an unambiguously dimensionless expression — for example `atan2((y_2 - y_1)/d, (x_2 - x_1)/d)` instead of `atan2(y_2 - y_1, x_2 - x_1)` — so the substituted form is dimensionless without further coaxing.

To **display** a dimensionless angle in degrees, re-attach `u.rad` at the very end and convert:

```python
# v is a dimensionless number representing an angle (in radians).
v_deg = (v * u.rad) | pc.convert_to([u.deg]) | pc.N
```

This pattern keeps the internal calculations clean (everything dimensionless) and only attaches units for human display.

### 5b. Per-symbol target units

For per-symbol target units inside a comprehension, store each as a **list** in a `_target_unit` dict:

```python
_target_unit = {A_ct: [u.mm], A_s_min: [u.mm], sigma_s: [u.MPa]}
_v = {k: v | pc.subs(eqn | params) | pc.convert_to(_target_unit[k]) | pc.N for k, v in _e.items()}
```

### 6. No `print()` in notebooks

`print()` produces raw stdout that lands as a verbatim block in the PDF — wrong font, no LaTeX, no table styling. Use the equivalent keecas/IPython mechanism:

- For named values: `show_eqn({sym: value})`
- For prose with inline math: `display(Markdown(f"$T_{{SLU}} = {params[T_SLU]:.1f~L}$"))`
- For tables: build a `pd.DataFrame` and call `df_to_latex(df)` (see references/tables_and_plots.md)
- For text-only summaries (a paragraph of explanation): write a markdown cell, not a print

The one exception: `print()` inside a `#| output: false` cell that exists purely to compute a value with no rendered output. Be precise about which cell option you reach for — they are not interchangeable:

- `#| output: false` — the cell *runs*, but its output (stdout, return value, displays) is **not** shown in the rendered PDF. This is the option that legitimately silences a `print()`.
- `#| echo: false` — the cell *runs* and its output *is* shown in the PDF; only the cell's **code** is hidden. A `print()` in such a cell would still appear in the rendered PDF. (Note: in this project's template, `echo: false` is already the default — code is hidden by default — so explicitly writing it is usually redundant.)
- `#| eval: false` — the cell is **not executed** at render time. Used on `%run` cells (see §15) and on placeholder/TODO cells; not appropriate for silencing a print, because the computation also doesn't happen.

Even when `#| output: false` is the right choice, prefer `display(Markdown(...))` so the output can be turned back on later by removing the option.

### 7. Dict-naming convention

Use the standard names — they propagate through the codebase and Sonnet will look for them:

| Name | What it holds                                                |
|------|--------------------------------------------------------------|
| `_p` | raw parameter inputs (with units)                            |
| `_e` | sympy expressions (usually via `pc.parse_expr`)              |
| `_v` | numeric values derived from `_e` via the pipeline            |
| `_l` | short descriptions per symbol (rendered inside LaTeX `\text{...}`); doubles as the source for cross-reference anchors via `generate_unique_label(_l)`. Keep entries short and LaTeX-safe — see §3 for placement rules |
| `_d` | only when there is no `_l` confusion; some older notebooks use `_d` interchangeably with `_l`. Prefer `_l` for new code. |

`_descr`, `_desc`, `_lab`, `_labels` and similar variants are not used and cause inconsistency. Stick to the table above.

### 8. Expression strings — keep them parseable

Inside `pc.parse_expr` strings:

- Use `^` (not `**`) for exponentiation. The string passed to `pc.parse_expr` is meant to read as pseudo-LaTeX — `^` matches how the expression will render, while `**` parses correctly but breaks the visual analogy between source and output. This is a deliberate stylistic choice: the eqn-dict is the source of truth for the LaTeX you see in the PDF, so it should *look* like LaTeX.
- Wrap `Max`/`Min`/`Piecewise` as strings; don't construct `sp.Max(...)` directly. Homogeneous string form means uniform rendered LaTeX:
  ```python
  _e = {
      c_min_req: "Max(c_min_dur + dc_dev, c_min_terreno)" | pc.parse_expr,
      A_s_min:   "Max(N(0.26)*f_ctm/f_yk*b*d, N(0.0013)*b*d)" | pc.parse_expr,
      s_max:     "Min(3*h, 400*u.mm)" | pc.parse_expr,
  }
  ```
- For numeric literals that should not be sympy `Rational`s, wrap in `N(...)`: `N(0.26)`, `N(0.0013)`.
- Units belong in the string when they have to: `"... * u.mm"` is allowed and common.

### 9. No whitespace padding in dicts

Black/Ruff collapses alignment anyway, and aligned diffs are noisier:

```python
# GOOD
_l = {
    f_ck: "resistenza caratteristica del calcestruzzo",
    f_yk: "resistenza caratteristica dell'acciaio",
    f_ctm: "resistenza media a trazione",
}

# BAD
_l = {
    f_ck:    "resistenza caratteristica del calcestruzzo",
    f_yk:    "resistenza caratteristica dell'acciaio",
    f_ctm:   "resistenza media a trazione",
}
```

### 10. Markdown cells — prose only, no duplicated formulas

If a formula is defined in `_e`, the markdown cell preceding the code cell should NOT restate it as `$$...$$`. The formula is rendered by `show_eqn` from `_e`; restating it in markdown duplicates logic that will drift.

```markdown
# GOOD — prose context, formula stays in _e
### Minimo per controllo fessurazione — EC2 § 7.3.2

Per flessione pura su sezione rettangolare si assume $k_c = 0{,}4$, $k$ funzione di $h$, $A_{ct} = b \cdot h/2$ e $\sigma_s = f_{yk}$ in prima istanza.
```

Single inline `$...$` references to symbols in prose are fine; full display equations belong to the code cell.

Also: one paragraph per logical line in markdown. Don't pre-wrap at 80 chars — Quarto handles wrapping.

### 11. Plots — Quarto cell options, not `plt.savefig`

```python
# GOOD — figure label and caption via Quarto, no manual file save
#| label: fig-coefficiente-esposizione
#| fig-cap: profilo del coefficiente di esposizione $c_e$ in funzione dell'altezza $z$
plt.plot(...)
plt.show()
```

```python
# BAD — saving a PNG yourself; Quarto loses the caption/label binding
plt.savefig('tangenti_fune.png', dpi=150, bbox_inches='tight')
plt.show()
```

Cell options (`#| label:`, `#| fig-cap:`, `#| tbl-cap:`) must live **in the same cell that produces the figure/table** — not in a setup cell.

### 12. Tables — `df_to_latex`, never `df.to_markdown()` or `print()`

```python
import sys
sys.path.insert(0, str((PATH_PREFIX / '../..').resolve()))
from _scripts.table_utils import df_to_latex

import pint_pandas
pint_pandas.PintType.ureg = u
pint_pandas.PintType.ureg.formatter.default_format = '.2f~P'

df = pd.DataFrame.from_dict(...)
df_to_latex(df)                     # default: longtable + booktabs + Italian locale
df_to_latex(df, precision=3)        # more decimals
```

If a table is built mid-cell (not the last expression), wrap it in `display()`:

```python
display(df_to_latex(df))
```

Same wrap rule applies to `show_eqn` inside `if/else` branches — without `display(...)` the output won't render.

### 13. Verification — `check()` with demand/capacity

`check()` internally uses `LessThan`, so the argument must be **demand divided by capacity**, not the other way around:

```python
# GOOD — T_hold is the demand on the bolt group, S is its capacity
_check = {T_hold / S: check((_T_hold_val / _S_val) | pc.N | pc.doit, 1)}

# BAD — capacity/demand inverts the meaning of LessThan
_check = {S / T_hold: check(_S_val / _T_hold_val, 1)}
```

### 14. Multi-value metadata

`_metadata.yml` fields like `altezza_sito` may be a scalar or a list. Always normalise, compute for each, then pick the governing value explicitly using a `key=` lambda — don't assume the list is sorted:

```python
_raw = metadata["commessa"]["altezza_sito"]
_altezze_sito = _raw if isinstance(_raw, list) else [_raw]
_as_max = max(_altezze_sito, key=lambda v: u.Quantity(v).to_base_units().magnitude)
```

Then either build a merged zone+derived table (one row per input value, columns for derived quantities) or compute once for each value and emit a markdown line stating which one governs.

### 15. Notebook naming and `%run`

Notebooks in `relazione/Azioni/` are named without an `azione_` prefix (folder context already implies it): `__vento.ipynb`, not `__azione_vento.ipynb`. Case-specific notebooks `%run` the base as the very first cell, before their own init cells:

```python
#| output: false
#| eval: false       # prevents double-execution during qbc compilation
%run __neve.ipynb
```

See §1 for why: running it first avoids clobbering both local symbols and the current notebook's own `config.*` settings — the current notebook's own init cell, which always runs after, has the last word on those.

## Final self-check before declaring done

Before telling the user a notebook is ready, walk through this list. Each item is a violation of the conventions above; treat any "no" as a TODO, not as an acceptable trade-off.

1. Init cell imports `from keecas.label import generate_unique_label`?
2. Every `symbols(...)` call uses an r-string, with `{}` around multi-char subscripts and `\` for Greek?
3. Every numeric value displayed in the notebook is produced by `pc.subs(...) | pc.convert_to(...) | pc.N` — no parallel numpy/float arithmetic populates `params`?
4. Every `show_eqn` that displays formulas+values uses the `[_p | _e, _v, _l]` slot pattern (or a documented subset thereof) with `label=generate_unique_label(_l)`?
5. Zero `print()` calls in code cells? (Replace with `show_eqn`, `display(Markdown(...))`, or a DataFrame + `df_to_latex`.)
6. `pc.convert_to(...)` arguments are basic-unit lists like `[u.mm]`, not compound units like `[u.mm**2]`?
7. Description dicts are named `_l` (not `_descr` / `_labels` / `_desc`)?
8. Markdown cells preceding a code cell do NOT restate as `$$...$$` what the code cell already produces?
9. Figures use `#| label: fig-...` and `#| fig-cap: ...` cell options, not `plt.savefig('name.png')`?
10. Tables use `df_to_latex(df)`, with `display(...)` wrapping when produced mid-cell?
11. Verifications use `check(demand / capacity, ...)` — not the inverse?
12. If the notebook reads metadata that may be a list, it normalises with `isinstance(..., list)` and picks the governing value with a `key=` lambda?
13. Any `%run` cell is the very first cell in the notebook — before its own init cells — so it can't clobber local symbols or the notebook's own `config.*` settings?
14. No whitespace padding aligning dict colons or `=` signs?
15. Every `pc.parse_expr` string uses `^` (not `**`) for exponentiation, so the source reads as pseudo-LaTeX?
16. If the notebook contains trig functions: no `* u.rad` attached to trig results, arguments are dimensionless (or written as ratios of like-unit quantities), and `pc.convert_to([1])` is used to strip residual units before trig consumes them?
17. `_l` entries are short LaTeX-safe phrases (no inline `$...$`, no long parentheticals); for `_e` blocks with wide formulas, `_l` is *not* rendered as a column — descriptive prose lives in the markdown cell above instead?

If you wrote a notebook quickly and aren't sure, re-read the resulting `.qmd` file once and tick each item explicitly.

## When something doesn't fit

These conventions cover ~95% of cases but you will encounter edge cases — a calculation that genuinely needs numpy for a simulation, an iterative `solve` that runs across hundreds of inputs, a plot of a parameter sweep, etc. The principle to fall back on:

> Anything that ends up *displayed in the report* — a formula, a value, a tabulated result — comes from the symbolic pipeline. Anything that is purely a *means of computation* (plotting hundreds of points, iterating an optimiser) can use plain numpy, but its result, if it appears in the report, must be re-derived through the pipeline.

If you're stuck, the easiest tie-breaker is: look at the closest analogous reference notebook in `relazione/Azioni/` or `relazione/Verifiche/` and mimic its structure.
